# Security

## Controls in place

| Area | Control |
|---|---|
| Authentication | scrypt password hashes (per-user salt); account lockout after 8 failed attempts (15 min); login/register rate limit per IP |
| Sessions | Random 256-bit token in an HttpOnly, SameSite=Lax cookie (Secure in production); only its SHA-256 is stored; server-side expiry; password change revokes all sessions |
| CSRF | Per-session token required in `x-csrf-token` on every state-changing cookie-authenticated request |
| API tokens | `as_…` bearer tokens, stored hashed; scopes (`read`, `write`, `execute`, `admin`); expiry; revocation; act with the creator's *current* role; revoked automatically when the member is removed |
| Authorization | Role checks (viewer/editor/admin/owner) on every mutating service call, not just in the UI; node types can require a minimum role (e.g. raw SQL and AI agent need admin) |
| Tenant isolation | Every tenant query filters by `workspace_id`; credentials load only within the execution's workspace; cross-tenant credential references fail validation (tested) |
| Credentials | AES-256-GCM with a random IV per record; AAD binds ciphertext to `workspace:id`; never returned to the browser; edits never read secrets back; OAuth tokens refreshed server-side |
| Redaction | Sensitive keys and known secret values are redacted from logs, step inputs/outputs, audit details and API responses; webhook auth/signature headers are dropped from trigger data |
| SSRF | Every user-configurable URL (HTTP step, polling, MCP servers, AI base URLs, SaaS calls) goes through an http/https-only client that rejects embedded credentials, checks **every resolved IP at connect time** (defeats DNS rebinding), blocks loopback/private/link-local/metadata/CGNAT/ULA ranges, revalidates every redirect hop, and strips auth headers on cross-origin redirects. SMTP and external PostgreSQL hosts are checked the same way. Exceptions require `OUTBOUND_ALLOWLIST` (`host:port`) |
| Webhooks | Unguessable per-workflow keys; optional shared-secret or HMAC-SHA256 verification (constant-time compare); WhatsApp `X-Hub-Signature-256` verified with the app secret; rate limits; body size limits |
| OAuth | Authorization code + PKCE (S256); single-use state bound to user and workspace, 10-minute expiry |
| Expressions | Custom parser/interpreter; no `eval`/`Function`; whitelisted pure functions; prototype-key blocking; no getter invocation; size, depth and step limits |
| Code execution | No shell, Python, JavaScript or SQL generated by models or users is executed, except the admin-only, parameterized, read-only-by-default PostgreSQL step written by a human admin |
| AI safety | Model output is untrusted: structured outputs are JSON-schema validated (one repair attempt); classification labels constrained by enum; user content is wrapped and declared as data; agent tools limited to admin-approved MCP tools with schema-validated arguments and a hard step cap; monthly token budgets |
| MCP | `/mcp` requires an API token; per-tool scope and role checks; every inbound and outbound call is audited; external tools are **disabled until an admin enables them**, with a separate "allow for AI" flag; tool descriptions and results are treated as untrusted |
| HTTP hardening | CSP, X-Frame-Options DENY, nosniff, referrer policy, HSTS when secure cookies are on; JSON body limits; global and per-route rate limits |
| Messaging compliance | WhatsApp sends require an explicit opt-in field; templates include an email opt-out line; CSV export neutralizes spreadsheet formula injection |
| Audit | Logins, failed logins, credential/workflow/table/form/member/token/MCP changes, runs, approvals |
| Data | Parameterized SQL everywhere; table row filters use parameter-bound JSON keys; checksummed migrations; retention for executions and table rows |

## Known limitations (be aware before production use)

1. **No SSO, 2FA or email verification.** Registration is open by default; set `ALLOW_REGISTRATION=false` after creating your account.
2. **Table permissions are per table** (minimum read/write role), not per individual record or per project.
3. **Key management:** `ENCRYPTION_KEY` is a single environment key. There is no KMS integration and no key-rotation command yet. Losing the key makes stored credentials unreadable.
4. **Rate limiting is in-memory per process.** Behind several API instances, use a shared limiter or a gateway.
5. **SMTP and PostgreSQL host checks** resolve DNS before connecting (a small TOCTOU window), unlike HTTP, which pins validated IPs.
6. **Webhook replay protection** relies on dedupe keys; there is no built-in timestamp tolerance check for providers that sign timestamps.
7. **The AI agent** can call only approved tools, but any tool marked "allow for AI" can be invoked with any schema-valid arguments. Grant it only to read-only or low-risk tools, and put an approval step before risky actions.
8. **Sub-workflows run inline** inside the parent's job; very long loops count toward the parent step's timeout.
9. The live provider adapters (Google, WhatsApp, HubSpot, Slack, Anthropic, Ollama, SMTP, external PostgreSQL) were not exercised against the real services in this environment.
10. `OUTBOUND_ALLOW_PRIVATE=true` disables private-network blocking in development and is ignored in production. Never use it on a shared server.
11. There has been no independent security review or penetration test.

## Reporting

Report vulnerabilities privately to the maintainers. Do not open public issues for them.
